# ADR-023：组织邀请制（批次 B6 的「邀请与组织绑定」子项）

- 状态：已实现（2026-11-12）
- 关联：`docs/PRD.md` FR-01、`ADR-021` §2.4 / §3.3、`docs/ROADMAP.md` §1 B6、`AGENTS.md` §4.6

## 1. 背景：先把范围冲突摆出来

`docs/PRD.md` FR-01 写的是「账号必须绑定组织」。B5（`ADR-021`）落了三张表和注册时的
`role` + `organization_code`，但 §2.4 明确**不强制绑定**：存量账号全无组织，
且「用一个谁都能填任意字符串的文本框假装实现必须绑定，比不做更危险」。
`ADR-021` 两次把补齐动作划给 **B6 的邀请制**：

- §2.4：「FR-01『账号必须绑定组织』由 B6 的邀请制补齐」；
- §3.3：「成员邀请的完整流程（发码、过期、撤销）——B6」，并注明「不许在 ROADMAP 里记成已达成」。

**文档内部冲突，如实登记**：`docs/ROADMAP.md` §1 的 B6 批次行写的是「岗位审核流（FR-03）
+ 邮箱/手机号作登录标识 + 改密」，没有邀请制；而批次收账时「下一步顺序」被写成
「B6（邀请制与组织绑定）」。同一个批次号下挂了两件不相干的事。

**本批裁定**：按 `ADR-021` 的划界做「邀请制与组织绑定」这一子项——它是 B5 的直接延续
（组织码已在库，只差发码 / 过期 / 撤销 / 兑换），也是 B10a 教师端看板的前置。
ROADMAP 的 B6 行同步拆成两个子项，审核流 / 登录标识 / 改密仍标 **0%**，不许记成已交付。
第 7 轮裁定（B6/B7/B10a/B10b 的动作入口须过 `app/core/deadline.is_expired`）约束的是
「对某条岗位做一次有后果的事」，邀请动作不碰岗位，本批不触发；**审核流那一半落地时必须接上**。

## 2. 决策

### 2.1 一张新表，不复用 `organizations.code`

`organizations.code` 是长期、不限次、不可撤销的组织标识，注册时可填一次。
邀请需要「发出、过期、限次、撤销、谁发的」这些状态，塞回组织行会让一个组织只能有一张有效邀请，
或者把组织表变成一张状态机。新增 `organization_invitations`：

| 列 | 约束 | 为什么 |
|---|---|---|
| `id` | CHAR(36) PK | 与全仓主键口径一致 |
| `organization_id` | FK→`organizations` RESTRICT | 删组织前必须先把邀请清干净 |
| `code` | VARCHAR(64) UNIQUE | 服务端 `secrets.token_urlsafe` 生成，落库前 `strip().upper()`；不复用组织码，避免「一个组织只有一个永久码」 |
| `role` | VARCHAR(20) + CHECK IN (`student`,`teacher`) | **刻意不含 `school_admin`**：一张可转发的码不该能造出第二个校长；校长本来能改成员角色，但那要经过端点并留审计 |
| `max_uses` / `used_count` | INT NOT NULL | 默认 1 次，上限 100；一张码给一届学生用时不必发 300 张 |
| `expires_at` | DATETIME(6) NOT NULL | 默认 7 天；过期即不可兑换 |
| `created_by` | FK→`users` RESTRICT | 谁发的要能追溯 |
| `revoked_at` | DATETIME(6) NULL | 撤销是打标，不物理删——删掉就查不出「曾经发过这张码」 |
| `created_at` | DATETIME(6) NOT NULL | 列表按 `(organization_id, created_at)` 复合索引倒序 |

**刻意不建 `(created_at)` 单列索引**（`tests/test_migrations.py` 那条判据也挡着）：
本批没有任何跨组织的「全平台邀请」查询，单列索引只是每次写入多一次维护成本。

### 2.2 两级判断，沿用 B5 的分工

- 发码 / 列邀请 / 撤销：路由层 `require_permission(ORG_MEMBER_MANAGE)` 判「有没有权限」，
  服务层 `_ensure_same_organization` 判「这条记录是不是你这个组织的」，被拒绝的跨组织尝试
  照例写 `result=denied` 审计（`ADR-021` §2.5）。
- 兑换（`POST /invitations/redeem`）：**只需登录**，不需要任何组织权限——还没加入组织的人
  按定义不可能有组织权限。它的边界靠「码有效 + 该账号尚无组织」两条业务规则，不靠角色。

### 2.3 兑换是一次事务，且要挡住超发

`organization_members.user_id` 有唯一键（B5 §2.1：一个账号目前只能属于一个组织）。
兑换流程：`SELECT ... FOR UPDATE` 锁住邀请行 → 校验存在 / 未撤销 / 未过期 / 未用尽 →
校验当前账号尚无组织 → `add_member` → `used_count + 1` → 写审计 → 同事务提交。
行锁不是装饰：两个请求同时兑换最后一张码时，不加锁会双双通过 `used_count < max_uses`
的读判断，然后一个撞唯一键、另一个把次数写成 2。

**四种不可用（不存在 / 已撤销 / 已过期 / 已用尽）对外是同一句 400 文案**，不区分细节——
否则这个端点就变成一枚「猜邀请码是否存在」的探针。

### 2.4 可见降级不适用，但「失败必须说人话」适用

B11a 的 AI 可见降级与本批无关；但所有 4xx 文案仍必须来自
`app/core/error_messages.py::ErrorMessage` 受信目录（G3 闸会拦路由里的中文字面量），
前端收到失败要在页面上显示 `role="alert"`，不是 `console.error`。

### 2.5 FR-01 的强制力：本批**仍未达成**，如实登记

本批把「绑定」从注册时一个可随便填的文本框，改成**可审计、可撤销、有时效**的管理员动作，
但**不改注册流程**：存量账号全部无组织，若现在强制「注册必须带邀请码」，
这些账号重新注册 / 换设备登录时就会撞墙，而迁移方案（批量补发邀请、按邮箱认领）
属于产品决策，不该由一个后端批次顺手替老板拍板。

因此：
- 「想加入组织只能凭有效邀请」——本批成立；
- 「所有账号必须属于某个组织」——**仍未成立**，ROADMAP 不许记成已达成；
- `ADR-021` §2.4 那句「跨组织不可见只在有组织的账号之间成立」继续有效。

### 2.6 审计动作白名单扩三条

`invitation.create` / `invitation.redeem` / `invitation.revoke`。
与 B5 同口径：审计写入不单独 commit，与业务同一个事务；审计失败 → 业务回滚。

## 3. 后果

- 正面：组织成员的增长第一次有了「谁批准、什么时候、批了什么角色」的证据链；
  邀请可回收；组织码不再承担「永久公开口令」的角色。
- 负面：多一张表、一次行锁；兑换是组织成员的唯一新入口，注册时的 `organization_code`
  仍保留（B5 行为不破坏），于是**同一个组织有两种加入方式**——这是兼容性代价，
  本批不擅自删 B5 的入口，等强制绑定方案拍板时一起收口。
- 风险：邀请码一旦被转发出去，在过期前任何登录账号都能兑换（限于一次）。
  本批不收邮箱 / 手机号白名单（那属 B6 另一半的登录标识改造），
  真要按人定向发码时需要补「兑换者名单」，见替代方案 3。
- 并发：`FOR UPDATE` 只在兑换路径上，发码 / 列表 / 撤销不加锁，量级（校内几百人）足够。

## 4. 替代方案

| 方案 | 为什么不选 |
|---|---|
| 复用 `organizations.code` 当邀请码，不建表 | 一个组织只能有一张永久、不可撤销、不限次的码；「谁发的 / 什么时候过期」无处可记，撤销只能改组织码（会让所有已加入成员的资料对不上） |
| 邀请码里编码组织与角色（自包含 token，不落库） | 撤销与限次必须服务端有状态，最后还是得落一张表；自包含签名还多一套密钥管理 |
| 邀请绑定具体邮箱 / 手机号 | 产品上更定向，但 `users` 今天手机号列根本不存在、邮箱可空，B6 另一半才做登录标识改造；本批不提前依赖一个还不存在的列 |
| 兑换时直接改 `users` 表加 `organization_id` 列 | 与 B5「角色挂成员关系、不挂 users」的决策冲突，且一个人将来属于多个组织时要再迁移一次 |
| 强制注册必须带邀请码，一次补齐 FR-01 | 存量账号全部无组织，强制等于把现有用户锁在门外；迁移方案需产品裁定（§2.5） |
