# ADR-020：FR-05 的「更新时间」与「数据新鲜度」——匹配响应为什么需要两个时间戳

- 日期：2026-11-10
- 状态：**已生效并已由批次 B3 实现**（同 PR 交付）。决策人：本 ADR 由我（编码 agent）拍板，依据老板 2026-11-10 第 8 轮「**你可以按照 roadmap 的开发顺序一直开发，不用暂停等我**」+ 第 9 轮「**全程不需要再和我确认，只最终结果交付**」；我仍按 §4.6 先写本 ADR 再动契约字段——第 8 轮的「无视文档的门槛和墙」我读成「**写 ADR 但不等批准**」，不是取消记录。
- 关联：`ADR-017` §4（B3 剩余那一格就是在它那儿登记的）、`ADR-013`（匹配链路本体）、`ADR-016` §2.5（版本轴三兄弟：这一对时间戳**不是**第四条版本轴，理由见 §2.3）、`docs/PRD.md` §7 FR-05、`docs/ROADMAP.md` §2 B3 行、`docs/API.md` §4.10 规则 9 与 §4.10.1 字段表

## 1. 背景与取证

FR-05 的最后一行是：「结果必须展示：**分数版本、更新时间和数据新鲜度**」。开工前逐条量过：

| 取证 | 结果 | 决定了什么 |
|---|---|---|
| `MatchMeta` 的字段（`app/schemas/match.py`）逐个核过 | 有 `weight_sum_used` / `matcher_version`，**没有任何时间戳** | 「更新时间」与「数据新鲜度」两格今天都无 |
| `docs/API.md` 里 `generated_at` / 「新鲜度」 | 零命中 | 这不是文档漂移，是契约里就没有 |
| `frontend/src/` 里 `weights_version` / `matcher_version` 的**显示** | 只有注释与类型，**没有任何一处渲染它们** | FR-05 那句「必须展示」在**分数版本**这一半上今天也没兑现——这是一条既存缺口，本 ADR 不顺手补，登记在 §5 |
| 写路径是否 bump 主体行 | `app/repositories/job_repository.py:386` 与 `app/repositories/student_profile_repository.py:483` 都在改内容时把 `updated_at = now` 写回主体行 | `data_updated_at` 只取主体行是**够的**；扫子行只是多几次读 |
| 库里时间精度 | `DATETIME` 秒级，UTC naive 存、东八区串出（`app/core/datetime_display.py`） | 测试**不许**断言「变大了几秒」，只能断言「等于来源行」 |

## 2. 决策

### 2.1 两格，各答一个问题

| 字段 | 回答的问题 | 来源 | 两个端点之间 |
|---|---|---|---|
| `meta.generated_at` | 这份**报告**是什么时候给的 | 应用时钟（`utc_now()` → 东八区 ISO） | 允许不同（两次请求两个瞬间） |
| `meta.data_updated_at` | 它背后的**数据**旧到什么程度 | `max(jobs.updated_at, student_profiles.updated_at)` | **必须逐字相同** |

只给 `generated_at` 是不可接受的：用户看到「刚刚生成」会以为岗位是新的，而岗位可能三个月前就过期了——那恰好是 `ADR-017` 花了一整条 ADR 去消灭的「读数看起来一致但其实各说一套」的形状。

### 2.2 取数不新写一套，`_gather` 带出档案行的时间戳

`_freshness(job, profile_updated_at)` 是纯函数，两个公开方法（`match()` 与 `requirement_match()`）共用；`_MatchInputs` 只多带**一个** `profile_updated_at`，而不是把整个可能为 `None` 的 `profile` 对象再塞回去（那个类自己的注释写明摊平是为了让调用方不必各自判空）。

### 2.3 它不是第四条版本轴

`ADR-016` §2.5 立的三条轴（权重表 / 写法判据 / 别名词表）回答的是「**规则换版了**」；这一对回答的是「**数据有多新**」。前者是常量、要 +1，后者每次请求都变、不能 +1。混进同一张表会让人以为 `data_updated_at` 变化意味着算法变化，那正是三条轴分工要防的对账事故。

### 2.4 没有档案时退化成岗位行，而不是报错或谎报

`max()` 的候选集合里只有岗位行；输出与「档案不存在」这一事实由 `matched.score == null` / `note` 那套既有语义负责，本 ADR 不新增第三种「没有数据」的表达。

## 3. 后果

- 代码：`app/schemas/match.py`（两个模型各 +2 格）、`app/services/match_service.py`（`_freshness()` + `_MatchInputs` 一格 + 两条组装路径）、`frontend/src/api/jobs.ts`（两个 `Meta` 接口各 +2 格类型，界面不显示，守则 C5）。
- 测试 **+4** 条（`tests/test_job_match.py` 末尾追加，全部逐字存在）：

| 判据 | 测试 |
|---|---|
| 两格形状 + `data_updated_at == max(岗位行, 档案行)` + 先后关系成立 | `test_match_response_reports_generated_at_and_data_updated_at` |
| 跨端点 `data_updated_at` 逐字相同、`generated_at` 各自合法 | `test_both_endpoints_report_the_same_data_updated_at` |
| 编辑档案后这一格等于**新的档案行时间戳**（不比秒差，避免脆弱断言） | `test_data_updated_at_follows_the_profile_edit` |
| 无档案时退化为岗位行且不炸 | `test_data_updated_at_falls_back_to_the_job_row_without_a_profile` |

- 响应契约加字段属 §4.6 事件，故有本 ADR；`docs/API.md` 加了规则 9 与 §4.10.1 两行字段表。
- **迁移：零。** 这两个数都是读侧算出来的，不写库、不加列。

## 4. 替代方案（都量过）

- **只给一个 `generated_at`**：省一格，代价是「刚刚生成」被读成「数据是新的」——这是 FR-05 写两个词的原因，不是我的修辞。
- **`data_updated_at` 扫子行取最大值**（`job_skills` / `skills` / `experiences`）：多 3–4 次读，换来的是一个与主体行**永远相同**的数（两条写路径都 bump 主体行，见 §1 取证）。等真出现「只动子行」的写路径再改，改点是 `_freshness()` 一处。
- **把新鲜度算成「距今多少天」返回给界面**：看起来更友好，代价是把时区、精度与「谁现在的时刻」这三件事从后端搬到前端，与 `ADR-017` §3 那条替代方案（「**前端自己比日期**：`ADR-011` 2.G 与 `stores/job.ts:32-33` 都禁止」）直接冲突。界面要显示几天前，用两格 ISO 串自己减——那才是它该干的活。
- **把它做成第四条版本轴**：见 §2.3，语义完全不同。

## 5. 留给他的 / 显式不做的

1. **FR-05「必须展示」的三格里，今天只有本 ADR 交付的后端契约**：`分数版本`、`更新时间`、`数据新鲜度` 在界面上**一格都还没显示**（`分数版本` 是既存缺口，不是本批弄丢的）。这一屏属于前端轨，改的是可见文案与布局，我不在后端 PR 里顺手做。
2. **它挂在哪一批由他说**：`docs/ROADMAP.md` 的前端轨 F1–F7 里没有「匹配卡补三格元信息」这一项（老板那 10 条清单也没提）。我不擅自新增一个 F 批次号——编号唯一来源是我自己立的规矩（§0），开新号需要他一句话。
3. 若他要的是「岗位三个月没更新就提醒」，那是**产品规则**（阈值 + 提示语），不是这两格字段能替的；现在两格已经给了，阈值判据放后端还是前端应当另拍——按本仓库既有方向，判据放后端。
