# ADR-001：MVP 形态选择响应式 Web

- 状态：已接受
- 日期：待填
- 决策人：A / B

## 背景

Word 产品文档要求“电脑、手机均能操作”，且提交要求“产品发布到外网，或 APP 可发行版本，或小程序发布，且有 10 个以上真人用户使用”。团队为 2 人，Phase 1 只做简历切片，需要在最短时间内让真实学生用起来并留下使用证据。

候选形态：

1. 响应式 Web（部署公网）
2. 微信小程序
3. 原生 App / 跨端 App
4. 桌面端 + 移动端两套

## 决策

**选择响应式 Web，部署到公网。**

- 前端：一套响应式页面，断点覆盖 375px 与 1280px；
- 后端：沿用现有 FastAPI 骨架；
- 部署：选择一个支持公网访问的托管平台，Phase 1 只要求可访问、可注册、可生成简历。

## 后果

正面：

- 一套代码覆盖手机与电脑，符合 Word 文档“均能操作”；
- 无需应用商店/小程序审核，发布周期可控；
- 真实用户只需链接即可使用，便于收集 5–10 份使用记录；
- 与现有 FastAPI 骨架一致，不需要新建端。

负面 / 代价：

- 无法使用小程序原生能力（微信登录、分享卡片）——Phase 1 不需要；
- 移动端体验不如原生 App——Phase 1 只要求主路径可用；
- 需要自行处理公网部署与 HTTPS——列入 T7 范围。

## 替代方案及不选理由

- **微信小程序**：审核周期不可控，且需要额外账号资质，与两人团队的时间预算冲突；分享传播优势在 Phase 1 不是关键。
- **原生 App**：开发与发布成本远超 Phase 1 预算，10 个用户阶段完全不必要。
- **桌面 + 移动两套**：维护成本翻倍，违反“最窄切片”原则。

## 后续复审条件

出现以下任一情况时重新评估：

- 真实用户中超过一半明确表示“不会用网页、只用小程序”；
- Phase 2 需要微信登录或社交分享作为核心增长手段；
- 公网部署成本或稳定性成为主要障碍。
