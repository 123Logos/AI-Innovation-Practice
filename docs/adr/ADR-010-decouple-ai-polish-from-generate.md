# ADR-010：AI 润色与简历生成解耦、四档润色与草稿态确认制

- 状态：已接受
- 日期：2026-11-04
- 决策人：本项目人类负责人
- 取代关系：**部分取代 [ADR-009](ADR-009-deepseek-byok-nonstream.md)** 的「`/generate` 默认走 AI」与「`use_fallback` 显式模板降级」两条决策；ADR-009 的 BYOK Key 生命周期、`deepseek-flash` + 非流式 + `thinking=disabled` + 30 秒预算、日志脱敏、以及「AI 不产 HTML、排版归模板」全部**继续有效并被本 ADR 继承**。
- 相关：ADR-006（多份简历）、ADR-007（DIY 排版与主题）

## 背景

ADR-009 把 DeepSeek 接在 `/resumes/generate` 的链路里：点一次「生成简历」= 润色 + 排版 + 落库，
一次调用出成品。上线后暴露四个问题：

1. **用户无法控制润色强度。** 学生想要的差别很大：有人只想改改语病和错别字，有人希望把经历
   重写成 STAR 结构。一键模式只有一种输出，改不动就只能整份重来。
2. **AI 结果直接落库，污染不可逆。** 润色后的文案当场写进 `resumes.content_html`，
   用户是在「已经生成完」之后才第一次读到它。模型若夸大或写错事实，简历已经生成了，
   而学生往往直接拿去投——这是会伤害真实用户的产品风险，不是代码风险。
3. **Token 成本与等待被绑死。** 每次想微调措辞都得重跑排版并落一份新简历行
   （`resumes` 是 append-only 的，一次生成一行），既烧钱又让「我的简历」列表堆出十几个
   半成品味。
4. **「AI 不可用时是否改用模板」的询问链路复杂。** ADR-009 为此引入了 `use_fallback` 字段、
   三个错误码、前端 `window.confirm` 二次请求。解耦之后这条链路整体失去存在意义：
   润色失败就报错让用户重试，模板生成根本不需要 AI。

人类负责人据此决定把两件事彻底拆开。

## 决策

### 1. `/resumes/generate` 退回纯模板渲染

- 不再调用 `DeepSeekCopyWriter`，不再需要 `X-DeepSeek-Key`，`use_fallback` 字段删除。
- **仍然只按登录用户从数据库读档案**（`student_profiles` / `skills` / `experiences` / `educations`），
  请求体只收 `title` 与可选 `profile_id`。T7.2 定下的「客户端档案字段一律不采信」安全边界
  **没有松动**，`test_generate_ignores_profile_fields_sent_in_request_body` 继续守护它。
  这条是本轮最容易被误读的地方，故显式写下：解耦改变的是「谁来做文案」，不是「谁的档案算数」。

### 2. 新增 `POST /resumes/polish`：纯计算，不落库

- 请求体：`profile` + `skills` + `experiences`（**来自前端草稿态**，允许尚未保存）+ `mode` +
  可选 `max_words`。
- 响应体：`ResumeCopy`（润色后的技能顺序 + 每段经历的 `description` / `responsibility`），
  与经历入参按下标一一对应。
- **零写库**：不碰 `resumes`、不碰 `student_profiles` / `skills` / `experiences`。
  这是「AI 结果不污染数据库」的服务端保证，前端确认制只是它的第二道闸。
- 该端点允许采信客户端传来的档案数据，是因为它**只回显、不持久化**，且发送对象是用户自己的 Key。
  作为交换，它必须有三重约束：必须登录（复用 `get_current_user`）、限流
  `POLISH_RATE_LIMIT = "10/minute"`（否则等于把我们的服务器变成烧用户 Token 的开放代理）、
  输入规模上限（技能 ≤ 50、经历 ≤ 20、单字段字符上限），超限走 422。

### 3. 四档 mode 与 Prompt 分工

| `mode` | 语义 | 长度目标 |
|---|---|---|
| `detail` | 细节：只修语病、错别字、标点与用词不当 | 与原文一致 |
| `medium` | 中幅：提升专业度、优化动词与表述 | 与原文相近 |
| `heavy` | 大幅：按 STAR（情境-任务-行动-结果）重写，突出业务价值 | 可比原文长 |
| `expand` | 扩写：在不偏离事实的前提下丰富细节 | **硬不超过 `max_words`** |

四档共用同一组硬约束，且它们比档位更重要：

1. **不得新增任何输入里不存在的事实**——公司名、技术栈、数字、奖项一律禁止；
2. **`heavy` 的「量化指标」只能引用输入中已出现的数字**；输入没有数字时必须用定性表述，
   不得虚构「提升 40%」这类措辞。简历造假会直接伤害用户，这条不是风格问题；
3. 经历不得删除，`index` 必须与输入一一对应；
4. 技能名必须与输入完全一致，只能排序与去重；
5. 只输出一个 JSON 对象。

### 4. 幻觉边界由服务端强制，而不是指望 Prompt

润色结果仍然经过 ADR-009 定下的四条合并规则（技能对不上就丢弃、漏掉的补回；
经历数量或下标不符即判契约违规；只替换文案，标题与起止时间不动；润色成空白时回落原文）。
模型输出不合规矩时返回 `AI_SERVICE_UNAVAILABLE`（502），**不返回半截结果**。

`expand` 的 `max_words` 在服务端硬保证：Prompt 里写要求，返回后按句号/分号边界截断到上限
（找不到边界才硬切）。理由与 ADR-009 同源——模型不可信，而用户要的是一条确定性承诺。
截断对用户可见（对比弹窗逐段展示），且结果只进草稿，不满意可以放弃。

### 5. 前端：草稿态确认制

- 「生成简历」按钮保持原位，只调 `/generate`，不再出现任何 AI 提示或降级询问。
- 新增「✨ AI 智能润色」按钮 → Element Plus 对话框选档位（选 `expand` 时才出现「最大字数」输入，
  默认 200）→「开始润色」带 Loading。
- 拿到结果后弹出**对比确认弹窗**，按经历分段左「原内容」右「润色后内容」，底部只有两个动作：
  - **放弃**：什么都不改；
  - **接受并同步到表单**：把文案写进 Pinia `resume.draft` 并 `markDirty()`，关闭弹窗。
- 接受之后**不自动保存**：右上角「保存修改」进入 dirty 高亮，必须用户手动点击才落库；
  落库后才谈得上再生成简历。AI 永远无法只凭一次润色就改动数据库。
- 表单侧只允许 AI 改动 `description` / `responsibility` 和技能顺序；标题、起止时间、
  教育经历、姓名联系方式一律不由 AI 写入。

### 6. 错误语义收窄到润色链路

`AI_KEY_MISSING`（400）/ `AI_KEY_INVALID`（401）/ `AI_SERVICE_UNAVAILABLE`（502，`retryable`）
三个码保留，但只可能来自 `/resumes/polish`。前端的两处配套约束必须跟着搬：

- Key 只随 `/resumes/polish` 发送，不再随 `/resumes/generate` 发送；
- 401 分流（`AI_KEY_INVALID` 不触发令牌刷新、不踢下线）原样保留，判断依据从 URL 换成 code，
  与端点无关。

## 后果

- 一次「润色 → 采纳 → 保存 → 生成」变成四次交互，比原来的点击一次多三步。这是刻意的：
  多出来的每一步都是用户在行使否决权。
- 后端出现两个语义不同的入口，`ResumeService` 同时持有模板渲染与文案润色两条路径，
  状态流转要从「一份请求出一份成品」改成「草稿态 → 确认 → 保存」两段式；
  `stores/resume.ts` 需要新增一个把 `ResumeCopy` 合并进 `draft` 的动作。
- `/polish` 采信客户端档案数据，因此它**不能**被当作可信输入参与任何持久化或鉴权判断；
  任何后续需求若想让 polish 直接写库，必须先推翻本 ADR。
- 限流按客户端 IP 计数（slowapi 进程内存储），多 worker 部署时每 worker 独立计数，
  与认证限流是同一个已知局限；换 Redis 存储属冻结项，不在本轮。
- ADR-009 的「三码分流 + 模板降级询问」实现被拆除，其测试同步迁移到 polish 链路；
  `use_fallback` 从 schema、service、依赖装配、前端类型与 22 个模板测试里一并移除。
- 真实 Key 下的四档输出质量、`expand` 的字数遵循度、`heavy` 是否真的忍住不编数字，
  本轮仍无法验证（不持有任何真实凭据）；Mock 测试只能证明「我们要求的指令确实发出去了」
  和「不合规的结果会被拦下」。

## 替代方案

- **保留 ADR-009 的一键模式，只加一个 mode 参数**：实现成本最低，但「AI 结果未经理解即落库」
  的核心风险一分没减，且仍要每次重跑排版。人类负责人以「不可控、浪费 Token」否决。
- **润色结果直接写库、前端只做展示**：用户第一次读到文案时它已经是既有事实，撤销要靠再次覆盖，
  与「防范 AI 幻觉污染数据库」的初衷相反。不采用。
- **纯前端润色（浏览器直连 DeepSeek）**：Key 与请求都不经过我们的服务器，隐私面最小。
  不采用：Prompt 与幻觉边界暴露在客户端可被任意篡改，且四档约束无法在服务端兜住；
  同时浏览器直连第三方 API 还要吃 CORS 与 Key 明文驻留前端的双重代价。
- **让模型直接返回整页 HTML**（ADR-009 的原方案）：仍然不采用，理由不变——
  `ResumePreview.vue` 的 `v-html` 注入路径、DOM 类名契约、主题变量与 A4 一页约束。
- **保留 `use_fallback` 以便润色失败时自动出模板**：解耦后模板生成与润色毫无关系，
  「失败自动改用模板」变成伪需求；留着它只会让错误语义多一条没人走的路。删除。
