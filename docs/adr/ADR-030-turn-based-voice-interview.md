# ADR-030: 回合制语音面试（B11b）

- 状态：已采纳（Accepted，ADR 先行，代码随本文件同分支落地）
- 日期：2026-11-14
- 关联需求：FR-07（语音 / 转写）；`ADR-022`（文本面试的会话与轮次契约）
- 关联裁定：第 19 轮「DeepSeek 提供整段 ASR（≤120s）与 TTS；B11b 定为回合制语音面试」、
  「`/v1/tools/asr` 与 `/v1/tools/tts` 进 BYOK 白名单（书面同意）」、`ADR-014` §3 的事实更正
- 前置：`ADR-009`（BYOK Key 的存放与出线）、`ADR-010`（哪些请求可以带 Key）、
  `ADR-022` §（a）两张表

## 1. 背景：这一批要解决的三件事

1. **形态已定，但「一回合」到底是什么没定**：`ADR-022` 的后续口径只写了「回合制」。
   不定清楚，实现时最容易滑向两条错路——做成实时双向（做不到：ASR **不支持流式**），
   或者把音频塞进 `interview_turns`（那就得建表、存盘、留一份没人会听的隐私数据）。
2. **音频是生物特征载体**：留一份音频就多一个泄露面，而产品上没有任何用途——
   复盘要看的是「说了什么」，不是「怎么说的」。所以「转写完毕即删」必须是**结构性**的，
   不能靠一句「记得删」的注释。
3. **BYOK 白名单要扩，而它是「逐条书面同意」那道闸**：`ADR-014` 的解冻**不覆盖**新 BYOK URL。
   老板第 19 轮已书面同意这两条，本 ADR 负责把「为什么是这两条、且只有这两条」写死。

## 2. 决策

### 2.1 一回合的定义（状态机）

一场语音面试就是 `ADR-022` 的那场文本面试，只是**候选人那一步可以走语音**：

```
候选人说话 ──► [浏览器录音，≤120s，≤8MiB]
                     │  （音频只在内存里，Blob）
                     ▼
             POST https://api.deepseek.com/v1/tools/asr   ← 前端直连，带用户自己的 Key
                     │  失败 → 降级为手动输入（可见提示）
                     ▼
              转写文本（纯字符串）
                     │  ★ 音频在这里被丢弃：不排队、不落盘、不上传我们的后端
                     ▼
       POST /api/v1/interviews/{id}/messages  {content, input_mode:"voice"}
                     │  后端只收到文本
                     ▼
        面试官的新一段（真实 AI 或既有降级模板）
                     │
                     ▼
             POST https://api.deepseek.com/v1/tools/tts  ← 前端直连，朗读面试官那段
                     │  失败 → 静默转纯文字（内容照常可读）
                     ▼
                  播放
```

四个不变量：

- **A. 音频一次都不经过我们的后端。** 没有 `/interviews/{id}/audio` 这类端点，
  也没有把 base64 塞进 `content` 的旁路。所以「不入库、不存盘」不是纪律问题，
  而是**网络路径上根本没有那条线**——这是唯一可被结构性验证的写法。
- **B. 一回合一次请求。** 不做流式（ASR 不支持；TTS 用整段合成），所以没有
  WebSocket、没有打断、没有 VAD。用户说完点「结束这段」才发。
- **C. 落库的是文本 + 一个模式标记。** `interview_turns.input_mode`（`text` / `voice`）
  只解释「这一轮是说的还是打的」，它**不是**音频的指针。
- **D. 两种降级都必须可见且可继续。** ASR 失败 → 页面切回文本输入并提示
  「语音识别失败，请手动输入」（不假装识别成功、不吞掉这一轮）；
  TTS 失败 → 只是不播声音，文字回复照常显示。

### 2.2 时长与体积约束（前端）

| 约束 | 值 | 为什么是这个值 | 谁来保证 |
|---|---|---|---|
| 单段时长 | ≤ **120 s** | DeepSeek ASR 的硬上限，超了直接失败 | 前端定时器到点自动停 |
| 单段体积 | ≤ **8 MiB** | 同上 | 停录后查 `Blob.size`，超了丢弃并提示 |
| 格式 | `16 kHz` 单声道 `WAV` 优先 | ASR 按**内容**判格式；16k 单声道是最省体积的可识别形态 | `MediaRecorder` 的 `mimeType` 协商 + 降级到浏览器默认 |

**为什么不裁掉超时的那段**：裁一段音频需要重编码（新依赖 + 主线程卡顿），而
「超出 120 秒」的正确反馈是「这一段太长了，请分段说」，不是悄悄丢掉后半句。

### 2.3 TTS 的取舍

- `voice_id` 固定 `stella`（默认女声），`format` 固定 `wav`。**不做音色选择**：
  这一批要证明「听得见」，不是「可以挑声音」。
- `filter_markdown: true`（默认）：面试官文案里偶尔有 `**` 这类强调符，念出来很怪。
- **超时 30 s 且失败即放弃**：TTS 是锦上添花，不值得为它卡住对话。
  中途断开（已开始返回后合成失败）同样视为失败——`ADR` 原文点名了这种半截响应，
  长度不足的音频当失败处理（`< 44` 字节连 WAV 头都不够）。
- 合成在**拿到文字回复之后**发起，不并行：文字是必需品，音频是附加品，
  并行只会让失败路径变成两个竞态。

### 2.4 BYOK：白名单扩两条，且只扩两条

`frontend/src/api/client.ts` 新增**直连实例** `deepseekHttp`
（`baseURL: https://api.deepseek.com`，**不挂我们自己的 JWT 拦截器**），
它的请求白名单是：

```ts
export const DEEPSEEK_DIRECT_PATHS = ['/v1/tools/asr', '/v1/tools/tts'] as const
```

三条硬约束，缺一条就不算落地：

1. **白名单是白名单**：不在表里的路径，请求拦截器**直接抛错，一个字节都不出网**。
   这与既有 `BYOK_KEY_PATHS`（「哪些我们的端点带 `X-DeepSeek-Key`」）是**两张表**：
   那张管「转发」，这张管「直连」。混成一张会让「我们的 JWT 会不会被发到 DeepSeek」
   这个问题失去机械答案。
2. **我们的 JWT 绝不出现在我方域名之外**：`deepseekHttp` 没有注入 access token 的拦截器，
   `Authorization` 头上只有 `Bearer <用户自己的 Key>`。反证见
   `byok.spec.ts` 的「直连实例不带我们的会话令牌」。
3. **只在这两条路上带 Key**：`/v1/chat/completions` 之类的路径即使前端拼对了 URL，
   也会被白名单拦下——本项目的 AI 文本能力一律走**我们的后端**（可审计、可降级、
   Key 不出服务端边界），前端直连只允许「音频进、音频出」这种**不产生业务文本**的调用。

> **为什么 ASR/TTS 反而要直连**：转写结果要立刻入库成为一轮 `interview_turn`，
> 音频本身不该离开用户设备；而 TTS 是纯渲染。把它们放到后端转发，等于让音频
> 穿过我们的进程与临时文件系统——那正是 §2.1 不变量 A 要避免的。代价是 Key 出现在
> 浏览器里（本来就在：BYOK 的定义），收益是「音频从不上传」。

### 2.5 数据模型：只加一列

`interview_turns` 加 `input_mode VARCHAR(8) NOT NULL DEFAULT 'text'`（迁移 `0027`），
取值 `text` / `voice`，`CHECK` 约束与代码枚举同源。

- **不建表、不建列存音频**：音频没有落点，这是 §2.1 的设计结果，不是待办。
- **不存 ASR 的 `request_id` / `duration_ms`**：它们描述的是「那次转写」，不是「这一轮内容」；
  真要排查，浏览器控制台里那条失败日志比库里的一列更有用（而且我们本来就不想存音频元数据）。
- 存量行 `input_mode='text'` 是**真话**：B11b 之前所有轮次都是打字来的。

### 2.6 端点清单（本批**不新增后端端点**）

| 方法 | 地址 | 谁调 | 是否新增 |
|---|---|---|---|
| `POST` | `https://api.deepseek.com/v1/tools/asr` | 浏览器（BYOK 直连） | 外部 |
| `POST` | `https://api.deepseek.com/v1/tools/tts` | 浏览器（BYOK 直连） | 外部 |
| `POST` | `/api/v1/interviews/{id}/messages` | 浏览器 → 我们 | **既有**，请求体多一个可选 `input_mode` |
| `GET` | `/api/v1/interviews/{id}` | 浏览器 → 我们 | **既有**，响应多一个 `input_mode` |

「零新增后端端点」是这一批的验收点之一：`app/` 里不会出现任何接收二进制的路由。

## 3. 后果

**好处**：音频零留存（结构性保证，不是纪律）；后端零新增依赖、零新增外部调用、
零新增表；语音与文字共用一条会话流，复盘页不需要区分两套数据结构。

**代价 / 如实登记**：

- **体验不如电话**：一回合要等「录音 → 转写 → 生成 → 合成」四段，且不能中途打断。
  这是 ASR 不支持流式的直接后果（`ADR-022` 已记账）。
- **依赖浏览器 `MediaRecorder`**：不支持的浏览器（老 Safari / 部分内置 WebView）
  直接退回文本模式，不做二次兼容——这一批的降级策略是「说出为什么不能用」，
  不是「想办法也能录」。
- **Key 在浏览器里**（BYOK 固有），且这两条直连路径**不经过我们的审计**：
  能用它的人只有 key 的持有者，但「谁什么时候转写了多少秒」我们看不到。
  按量计费的风险由用户自己承担，这与 `ADR-009` 的既有口径一致。
- **`input_mode` 只是标记**，不参与任何打分或统计；将来若要「语音作答的评分是否更低」
  这类分析，得先有一次真实数据，再决定要不要加证据列。

## 5. 遗留与下一步

1. **不做流式 / 打断**：要做得先有流式 ASR，`ADR` 里没有排期；
2. **不做录音回放**：音频不留存，所以「听听我刚才怎么说的」这类复盘功能与本 ADR 互斥，
   要做必须另起一份 ADR 说清留存期限与访问控制；
3. **不做多语言显式选择**：ASR/TTS 都按文本自动判语种，与产品「中文为主」一致；
4. **不做后端审计**：直连调用不经过我们的进程，这一点在 §3 如实登记，不假装有账。
