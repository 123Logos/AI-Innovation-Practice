# ADR-022: 文本模拟面试会话存储与降级策略

- 状态：已采纳（Accepted）
- 日期：2026-11-12
- 关联需求：FR-07（文本模拟面试，批次 B11a）
- 负责人：interview-line

## 背景

批次 B11a 要实现「文本模拟面试（FR-07）」：用户与 AI 面试官进行一次纯文本的问答式模拟面试。
AI 面试官基于用户的简历、目标岗位（可选）和默认学生档案出题，并在每轮对用户的回答给出反馈。
本 ADR 只覆盖 B11a 这一期：纯文本、单场会话、不建媒体房间、不建正式评估报告表（评估报告留待
后续 B11b 批次）。需要决策的核心问题有四个：

1. 一次面试的问答历史该如何持久化——是拆成两张关系表，还是塞进单个 JSON 字段？
2. AI 不可用时（无 Key / 超时 / provider 错误）会话如何继续，且用户必须能**看见**降级而非被静默欺骗。
3. 面试题从哪里来（简历？岗位？用户填的目标岗位？），数据不足时怎么办。
4. 上下文长度如何控制，避免无限累加历史把 prompt 撑爆。

## 决策

### （a）两张表而非一个 JSON 字段

采用两张表：

- `interview_sessions`：一场面试的元信息。列含 `id`(主键，36 位 UUID 字符串)、
  `user_id`(所有者，指向 `users.id`)、`job_id`(可选目标岗位，指向 `jobs.id`，可空)、
  `status`(`active` / `ended`)、`target_role`(用户填写的目标岗位名，可空)、
  `created_at`、`updated_at`、`ended_at`(可空)。
- `interview_turns`：每一轮问答。列含 `id`、`session_id`(外键指向 `interview_sessions.id`，
  RESTRICT)、`sequence`(该会话内从 1 递增的序号)、`speaker`(`interviewer` 或 `candidate`)、
  `content`(文本内容)、`ai_degrade_reason`(可空：当该轮 interviewer 内容因 AI 失败而降级时记录原因)、
  `created_at`。

理由：

- **查询与可观测性**：列表页要展示每场会话的标题/状态/时间，详情页要按 `sequence` 顺序回放
  turns。关系表用普通 `SELECT ... ORDER BY sequence` 即可，而 JSON 字段需要解析、无法在数据库层
  做范围查询与索引，也不利于后续做「按会话聚合统计」「审计」。
- **流式与增量写入**：面试是逐轮进行的，每轮落一条 turn 比「读出整段 JSON → 追加 → 写回」更安全、
  并发更友好，也不会因为一次写入过大而失败。
- **降级可追踪（直接服务于问题 b）**：每一轮 interviewer 的发言是否「真由 AI 产生」需要在数据上
  留下证据。`ai_degrade_reason` 列让降级这件事成为**一等公民**——既能在响应里告诉用户，也能在
  事后审计时确认哪一轮是降级产物。
- **迁移与演进**：后续 B11b 若要做评估报告、打分，直接在 sessions 上加列或在 turns 上加反馈列即可，
  不必重构一个巨型 JSON schema。

JSON 字段的唯一合理场景是「结构化配置」，而面试历史的本质是**有序事件流**，关系模型更贴合。

### （b）AI 不可用时：可见降级，绝不静默

AI 调用统一走既有的 DeepSeek 适配器（与 `evidence_scorer.py` / `match_service.py` 同一套），
异常层级为 `EvidenceScoreError` 及其子类（`AuthError` 401 / `UnavailableError` 非 401 /
`TimeoutError` / `BadOutputError` / `EmptyContentError` / `TruncatedError`）。

降级规则（照搬 `match_service.py` 的范式，在 **service 层**就地 catch，不抛到端点）：

- service 调用 AI 时捕获上述异常，将其翻译成一个人类可读的 `degrade_reason` 字符串
  （如「AI 服务暂不可用，已为你生成通用面试问题」「未检测到可用的 AI 密钥，已切换到离线模式」）。
- 该轮的 `speaker=interviewer` 内容**仍然生成**——但内容由本地降级模板产出（基于简历/岗位/默认题库
  拼出一道通用题），并在 `interview_turns.ai_degrade_reason` 与响应体里**显式打标**。
- 端点**保持 200**，不触发 `app/main.py` 的 AI 错误处理器；会话继续，用户可继续作答。
- **绝不让用户误以为「AI 说了这句」而实际没说**：降级内容在 UI 上有可见标识（如「离线模式生成的题目」），
  响应体 JSON 里带 `ai_degrade_reason` 字段（非空即代表此轮非真 AI）。

这满足「可见降级而非静默」：用户永远能区分「真 AI 回复」和「降级兜底」。BYOK 密钥来自请求头
`X-DeepSeek-Key`，在依赖装配处读取；密钥为空或无效时同样走降级（降级原因是密钥缺失/无效），
绝不把密钥日志化或落库。

### （c）面试题来源与数据不足时的行为

出题意向优先级（从高到低）：

1. 若本次会话绑定了 `job_id`，从岗位的职责/要求中提取面试题方向（复用既有的岗位数据）。
2. 若用户填写了 `target_role`（文本），据此生成该方向的通用题。
3. 若用户有默认学生档案（student_profiles），结合其经历/技能出题。
4. 以上皆无，回落到**内置通用面试题库**（与具体岗位无关的行为/自我介绍/动机类问题）。

数据不足行为：任何一层缺失都不阻断会话，只是逐步回落到更通用的题源；若连简历/岗位/档案/目标岗位
都没有，则全程走通用题库，并在会话创建响应或首轮 `ai_degrade_reason` 中提示「将使用通用面试题目」。
AI 完全不可用时（见 b），则由本地模板按上述同一优先级回落出题，保证会话始终可开始、可继续。

### （d）上下文长度控制

- **turn 截断**：向 AI 发送上下文时，按 `sequence` 取最近 N 轮（默认 10 轮，常量可调，作为证据写进
  service），超出部分截断；首轮始终携带「面试设定」（岗位/目标/简历摘要）作为系统背景，不计入轮数上限。
- **证据**：每次 AI 调用前在 service 里计算 `truncated = len(all_turns) > N`，并将
  `context_turn_count`（实际送入的轮数）与 `truncated` 标记随响应返回，使「是否被截断」对用户/审计可见。
- 文本列 `content` 为 `TEXT`，不做硬性字符截断（由 AI 适配器与 prompt 约束长度）；但若单轮异常超长，
  由 service 在上屏前做安全裁剪并记录。

## 后果

- 正面：面试历史可查询、可审计、可增量写入；降级在数据与 UI 两层都有证据，符合「可见降级」
  红线；题源与上下文策略可演进。
- 负面 / 代价：比单 JSON 字段多一张表和若干写入；需要在 `tests/conftest.py` 的 `APP_TABLES` 中
  按子表先于父表补入 `interview_turns` 与 `interview_sessions`；需要在 Alembic 新增迁移。
- 风险：上下文截断阈值 N 若设得过小会影响体验，设得过大有成本——先用 10 轮常量，后续按实测调。

## 替代方案

1. **单 JSON 字段（如 sessions 里一个 `turns_json` 列）**：写入简单，但无法按轮查询/索引、难审计、
   降级难追踪、并发回写易冲突。否决。
2. **事件溯源 / 独立事件表 + 投影**：过度设计，B11a 期不需要。否决。
3. **AI 失败时直接返回 4xx/5xx 阻断会话**：违反「可见降级」要求，会让用户误以为功能坏了或被迫中断。
   否决。采用 service 层降级 + 200 + 显式打标。
4. **把降级内容也当成真 AI 返回（不标记）**：直接违反「绝不让用户误以为 AI 说了这句」红线。否决。
