# ADR-002：AI 能力先用 stub/模板，Phase 1 不接真实模型

- 状态：已接受
- 日期：待填
- 决策人：A / B

## 背景

Word 文档的核心功能之一是“根据同学已掌握的技能和项目经历，AI 自动生成简历”。现有骨架已规划 DeepSeek 适配器，但尚未接入真实调用。

Phase 1 的验收标准是：**生成结果整洁规范、不超过一页 A4、字段完整、可编辑**。它不要求文采、不要求个性化措辞、不要求真实模型参与。

若 Phase 1 直接接真实模型，会引入：API Key 管理、调用配额与费用、延迟与超时、输出不稳定导致的一页约束失效、测试不可重复等问题，全部与“先跑通链路”目标冲突。

## 决策

**Phase 1 采用“adapter 接口 + stub/模板实现”，不接真实 DeepSeek。**

具体：

1. 在 `integrations/` 下定义 `ResumeGenerator` 接口：输入结构化学生数据，输出 HTML 简历；
2. Phase 1 提供 `TemplateResumeGenerator` 实现：基于固定模板渲染，不调用外部网络；
3. 真实模型实现（`DeepSeekResumeGenerator`）只保留文件与接口签名，标注 `# PHASE-2: not wired`，不进入启动路径；
4. 测试全部使用 stub 实现，保证可重复、无网络依赖；
5. 服务层只依赖接口，不依赖具体实现，通过依赖注入选择实现。

## 后果

正面：

- 主链路（登录→填表→生成→预览→保存）可在无外部依赖下跑通并测试；
- 生成结果稳定，一页 A4 约束可被测试验证；
- 无 API Key、无费用、无超时，CI 可离线运行；
- 后续接真实模型时，只需替换实现，不改 service/route。

负面 / 代价：

- Phase 1 的简历“智能感”有限，真实用户可能反馈“像填表”；
- 需要在 Phase 2 补做 prompt 设计、输出校验、失败降级；
- 若真实用户强烈要求“AI 润色”，可能提前触发 Phase 2。

## 替代方案及不选理由

- **Phase 1 直接接真实 DeepSeek**：引入外部不稳定因素，测试不可重复，与“先验证链路”目标冲突；且真实模型输出长度不可控，一页约束难保证。
- **完全不做生成，只做手工填写**：偏离 Word 文档核心功能，无法验证“生成”这条链路。
- **用本地小模型**：部署与资源成本高，Phase 1 不必要。

## 后续复审条件

- 简历切片通过 5 名真实用户验证；
- 用户反馈中“需要 AI 润色/个性化”出现频次 ≥ 3；
- 已有稳定的输出校验与长度控制方案（如结构化输出 + 字数约束 + 失败重试）。
